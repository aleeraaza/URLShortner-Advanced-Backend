# Authentication system: how this one works, and the interview version

This document explains the design behind `backend/src/modules/auth`. The first document explains the files and the syntax. This one explains the security ideas, the request flows, and the questions an interviewer asks about a system like this.

The implementation is a hybrid:

- The access token is a signed JWT. The API can accept it without reading the database.
- The refresh token is also a signed JWT, and the server stores a hash of it in the `sessions` table. Logout and "logout everywhere" work by deleting rows.

That hybrid is the thing to be able to say out loud.

---

## 1. Authentication and authorization

Authentication answers "who is this caller?". In this code, `authenticate` does that. It verifies the access token and sets `req.user`.

Authorization answers "is this caller allowed to do the thing?". `authorize("USER")` does that. It runs after `authenticate` and compares `req.user.role` with the roles the route allows.

A failed authentication is 401 Unauthorized. A failed authorization is 403 Forbidden. The words in the HTTP spec are slightly confusing: 401 means "I do not accept your credentials", and 403 means "I know who you are, and you still cannot do this".

Login is not authentication middleware. Login is the exchange of a password for credentials. The middleware is the check on later requests.

---

## 2. What we store about a user

The `users` table stores:

- `id`, a CUID2 generated by the database
- `email`, unique
- `passwordHash`, a bcrypt string
- timestamps

The plaintext password is never stored and never logged. It arrives in `req.body`, is hashed inside `register`, and is dropped. Login uses it once, inside `bcrypt.compare`, and does not write it anywhere.

The `sessions` table stores one row per login:

- `userId`
- `refreshTokenHash`
- `expiresAt`
- `userAgent` and `ipAddress`
- `createdAt`

A person who logs in from a laptop and a phone gets two rows. Each row is one device session. "Log out" deletes one row. "Log out of all devices" deletes every row for that user.

## 3. Password hashing

### What a hash is

A cryptographic hash takes an input of any size and produces a fixed-size fingerprint. The same input always produces the same output. You cannot reconstruct the input from the output. Good hashes also make it impractical to find a second input with the same output.

SHA-256 is a fast hash. bcrypt is a slow hash built for passwords.

### Why passwords use bcrypt

If the database leaks, the attacker has `passwordHash` and not the password. With a fast hash and no salt, they can hash a dictionary once and look the stolen hashes up in it. That table is called a rainbow table when it is built to invert hashes in bulk.

bcrypt is built to make that expensive:

- It generates a random salt and stores the salt inside the hash string. Two users with the same password get different hashes. A precomputed table for one hash does not work for the other.
- It repeats the work many times. `BCRYPT_ROUNDS = 12` means `2^12` (4096) iterations of the internal key setup. Checking one guess takes real time. Checking a billion guesses takes a data center.
- The cost is a parameter. Hardware gets faster, and you raise the rounds. Old hashes still verify, because the rounds and the salt are inside the stored string.

`bcrypt.compare(password, passwordHash)` reads the salt and the rounds out of `passwordHash`, hashes the password the same way, and compares in a way that does not stop at the first different byte. That last property matters against timing attacks on the comparison itself.

A bcrypt hash looks roughly like `$2b$12$<22 char salt><31 char hash>`. You do not parse it yourself.

### The 72-byte limit

bcrypt uses the first 72 bytes of the password and ignores the rest. The register schema rejects passwords longer than 72 characters so two different long passwords cannot collapse to the same hash without the user knowing. The unit is bytes in bcrypt and characters in the schema. For typical passwords those match. A password full of multi-byte characters could still be under 72 characters and over 72 bytes. That edge is worth knowing in an interview.

### Why the refresh token does not use bcrypt

A refresh token is a JWT. It is long, well over 72 bytes, and it is already a high-entropy secret signed with the server secret. bcrypt would truncate it, and bcrypt is slow on purpose.

We need a fingerprint we can store and compare for equality. SHA-256 does that in microseconds, has no truncation, and is deterministic: the same token always produces the same hex string, so we can look the session up conceptually by comparing hashes. The column is unique, which also stops two sessions from storing the same fingerprint.

SHA-256 is the wrong tool for passwords because it is fast and, used alone, has no salt. It is the right tool for a token that was generated with 256 bits of signing secret behind it. An attacker who steals the hash still does not have a token they can send. The server hashes whatever the client presents and compares. The hash itself is not accepted as a bearer token.

### A gap you should mention honestly

In `login`, if the email does not exist, the code skips `bcrypt.compare`. If the email exists, it runs bcrypt. Those two paths take different amounts of time. An attacker who can measure responses carefully can guess which emails are registered, even though the JSON message is the same.

The usual fix is to compare against a precomputed dummy hash when the user is missing, so both paths do the same work. This code does not do that yet. The identical error message still stops the easy version of account enumeration.

## 4. JSON Web Tokens

### The three parts

A JWT is three base64url strings separated by dots:

```text
header.payload.signature
```

The header says how it was signed. Here that is HMAC-SHA256 (`HS256`). The payload is JSON. The signature is HMAC of `header.payload` using the server secret.

`jwt.sign` builds all three. `jwt.verify` recomputes the signature and checks the `exp` claim.

### Signed, not encrypted

Anyone who has the token can base64-decode the payload and read it. The signature stops them from changing it. If they change `sub` to someone else's id, the signature no longer matches and `jwt.verify` throws.

So the payload must be data you are willing to reveal to the client: user id, email, session id, token type, expiry. A password, a hash, or a secret does not belong there.

### The two payloads in this project

Access token:

```ts
{ sub: userId, email, sessionId, type: "access" }
```

Refresh token:

```ts
{ sub: userId, sessionId, type: "refresh" }
```

`sub` is the registered JWT name for the subject. Using it, instead of a custom `userId` claim, matches libraries and interview vocabulary. Our `verify` functions read `payload.sub` and the rest of the app calls it `user.id`.

`type` is our claim. Access and refresh also use different secrets, so a refresh token fails `jwt.verify` against the access secret even before the `type` check. The `type` check is defense in depth if those secrets were ever the same, and it documents intent.

`email` is only on the access token because `req.user` wants it without a database read. It can go stale if the user changes their email. This project has no email-change route. If you add one, you should know old access tokens still carry the old email until they expire.

### Expiry

`JWT_ACCESS_EXPIRES_IN` defaults to `15m`. `JWT_REFRESH_EXPIRES_IN` defaults to `7d`. `jwt.sign` writes an `exp` claim, unix seconds. `jwt.verify` rejects a token past that time.

The session row also has `expiresAt`, set to now plus 7 days. Refresh checks both. The JWT expiry is inside the token. The column is the server's copy, and rotation extends it.

Short access tokens limit the damage of a stolen access token. Long refresh tokens are what make the user stay logged in. The refresh token is the one we can revoke, because it is stored.

### Secrets

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are separate, each at least 32 characters, from `.env`. They are the HMAC keys. Anyone who has a secret can mint tokens the server will trust. They stay out of git and out of logs.

Rotating a secret invalidates every token signed with the old one. There is no key id (`kid`) in this project, so rotation is all-or-nothing.

## 5. Where the tokens live

Login and register do two things with the new tokens:

1. Set two cookies, `accessToken` and `refreshToken`.
2. Put `accessToken` in the JSON body. The refresh token is absent from JSON.

### Cookie flags

| Flag | Value here | What it does |
|---|---|---|
| `httpOnly` | `true` | `document.cookie` cannot read it. A script injected into the page (XSS) cannot steal it that way. |
| `secure` | `true` in production | The browser sends it only over HTTPS. |
| `sameSite` | `lax` | The browser sends it on same-site requests and on top-level navigations. It does not send it on cross-site POSTs from another site, which blocks the common CSRF form attack. |
| `maxAge` | the token lifetime | The browser drops the cookie on schedule. |
| `path` | `/` | Sent for every path on this host. |

`httpOnly` does not stop XSS from calling your API. The browser will still attach the cookie to `fetch` from the page. What it stops is the attacker copying the token to their own machine. That distinction is a common interview follow-up.

### Bearer header

`readAccessToken` prefers `Authorization: Bearer <token>`, then the cookie. Mobile apps and server-side clients often cannot rely on browser cookies, so they store the access token themselves and send the header. Browsers can use the cookie and ignore the header.

### CORS and cookies

A browser will not send cookies on a cross-origin request unless:

- the server responds with `Access-Control-Allow-Credentials: true`, which `credentials: true` in the CORS middleware sets, and
- the allowed origin is a specific origin, which `FRONTEND_URL` is. `*` is illegal together with credentials.

The frontend must call `fetch` with `credentials: "include"`. Otherwise the browser hides the cookies from that call.

### CSRF, briefly

CSRF is "another website makes the victim's browser call your API, and the browser attaches the victim's cookies". `sameSite: "lax"` stops that for cross-site POST. It does not stop a GET navigation. Our mutations are POST, so the dangerous case is covered by `lax`.

A bearer token in a header is not sent automatically by the browser, so classic CSRF does not apply to header-only clients. The cost is that JavaScript must be able to read the access token, which means XSS can steal it. Cookies and memory-stored bearer tokens trade XSS theft against CSRF. This API accepts both, and the refresh token is cookie-only so page JavaScript never sees the long-lived credential.

## 6. Login, including from a second device

`login`:

1. Find the user by email.
2. `bcrypt.compare` the password with `passwordHash`.
3. On failure, 401 with one generic message.
4. On success, open a new session.

Opening a session always inserts a new row. It does not delete older rows. The laptop session stays valid when the phone logs in. That is "logged in on all devices". Each device has its own refresh token and its own row.

The new row records:

- `userAgent`, from the `User-Agent` header. Browsers send a string naming the browser and OS. It is a label for "which device was this?", useful in a session list and in an investigation.
- `ipAddress`, from `req.ip`. Express sets that from the TCP connection. It is a label for "which network was this?".

### Why store the IP if we never check it

We do not accept or reject a refresh because the IP matches. People change networks constantly: Wi-Fi to mobile data, office to home, a phone hopping cell towers. Binding the session to an IP would log them out for moving.

The stored IP is an audit field. If a user says "I didn't log in", you can look at the session rows and see a user agent and an IP that are not theirs. It is evidence, not a credential.

Limits you should say in an interview:

- The client can send any `User-Agent` they want. It is not authenticated.
- `req.ip` is the address of the TCP peer. Behind a reverse proxy or a load balancer, that peer is the proxy, unless Express is configured with `trust proxy` and you read the forwarded header carefully. This app does not set `trust proxy`. On your machine, `req.ip` is the local client. Deployed behind a proxy, it may be the proxy until that setting exists.
- `X-Forwarded-For` can be spoofed if you trust it blindly. Trusting the header only from your own proxy is the correct deployment step. It is not in this code yet.
- IP addresses are personal data in a lot of jurisdictions. Storing them means you should know why and for how long. Here the reason is session audit, and the row lives until logout, logout-all, expiry on refresh, or user deletion (cascade).

## 7. Calling a protected route

`GET /api/auth/me` with the access token:

1. `authenticate` reads the bearer token or the access cookie.
2. `jwt.verify` checks the access secret and `exp`.
3. The middleware writes `req.user` from the payload and sets `role` to `"USER"`.
4. `authorize("USER")` allows the role.
5. The controller calls `service.me(user.id)`, which loads the public profile from the database.

Step 5 is a database read because the profile includes `createdAt`, which is not in the token. The authentication decision itself was the JWT check.

There is no role column. Every access token is treated as `USER`. `authorize` is ready for an `ADMIN` role the day a token starts carrying a real role and a route asks for it.

## 8. Refresh, rotation, and reuse detection

Access tokens last 15 minutes. When one expires, the client calls `POST /api/auth/refresh-token` with the refresh cookie (or `{ "refreshToken": "..." }`). That route deliberately does not use `authenticate`. The access token being expired is the normal case.

### Rotation

A successful refresh does not reuse the same refresh token. It:

1. Verifies the refresh JWT.
2. Loads the session.
3. Confirms the hash of the presented token equals the stored hash.
4. Signs a new access token and a new refresh token for the same session id.
5. Overwrites `refreshTokenHash` and pushes `expiresAt` forward by 7 days.
6. Sets new cookies.

The old refresh token still has a valid signature until its original `exp`. The server rejects it anyway, because its hash is no longer the hash on the row.

This is refresh-token rotation. Stealing a refresh token is only useful until the real client refreshes. After that, the stolen copy is stale.

### Reuse detection

If a stale refresh token shows up after rotation, two things might have happened:

- The legitimate client retried and sent the token it already consumed.
- An attacker is using a stolen token, and the real client has already rotated.

The code cannot tell those apart. It takes the strict option: delete every session for that user, and return 401 with "Refresh token reuse detected. All sessions were revoked." The real user has to log in again with their password. The attacker loses every stolen refresh token too.

The check is specifically: the JWT verified, the session exists, the user id matches, and the hash does not. A random garbage string fails at `jwt.verify` and does not wipe sessions. A token for a deleted session fails the "session exists" check and does not wipe other sessions.

### The window this does not close

Two refreshes with the same token at the same moment can both read the old hash, both decide it matches, and both write a new hash. The second write wins. One of the clients is left holding a token that will later look like reuse, and the next attempt revokes everyone.

Closing that window needs a transaction that locks the session row, or a compare-and-swap update that only writes if the current hash is still the one we read. This code does the read and the update as separate queries. Say that if an interviewer pushes on race conditions. It is a real limitation, and the failure mode is "user gets logged out", which is the safer failure.

### Why `openSession` writes twice

The session id is generated by the database on insert. The refresh JWT must contain that id, and the stored hash must be the hash of that JWT. So register and login:

1. Insert with a random placeholder hash, just to obtain an id and satisfy the unique column.
2. Sign the real tokens with that id.
3. Update the hash to the real token's hash.

The placeholder is the SHA-256 of 32 random bytes. It is never given to the client. If the process dies before the update, the client never received a refresh token, and the row is an orphan session that cannot be refreshed. The user can log in again.

## 9. Logout and logout of all devices

### One device

`POST /api/auth/logout` requires a valid access token. The session id inside that token selects the row. The service deletes that row. The controller clears both cookies on this browser.

The phone has a different session row, so the phone stays logged in. Its refresh token still matches its own row.

### All devices

`POST /api/auth/logout-alldevices` deletes every session for `req.user.id`, then clears cookies on the device that made the call.

Other devices still have cookies. Their next refresh loads a session that is gone and gets 401. They must log in with the password again.

### The 15-minute leftover

`authenticate` does not read the `sessions` table. After logout, a stolen or leftover access token still works until its `exp`, up to 15 minutes. The refresh token is dead immediately, so the attacker cannot get a new access token.

That is the standard tradeoff of a stateless access token. Ways to close it, if an interviewer asks:

- Check the session row on every authenticated request. Simple, and it costs a database read per request. Logout then kills the access token immediately, as long as you also store the access token's id or treat "session missing" as logged out.
- Keep a short denylist of revoked access-token ids until they expire. Same idea, smaller read, usually Redis.
- Keep the access token as short as you can tolerate. 15 minutes is already that compromise.

This project chose the short access token and a stateful refresh token, and did not add the per-request session check.

### What logout does not do

Clearing cookies affects the browser that received the response. It does not reach the phone. The database delete is what reaches the phone, on its next refresh.

Logout also does not change the password. A stolen password still works. "Log out everywhere" plus a password change is the full response to a stolen password. Password change is not implemented. If you add it, it should call the same `deleteAllSessions`.

## 10. The whole life of an account

```text
register
  hash password with bcrypt
  insert user
  insert session (placeholder hash)
  sign access JWT (15m) and refresh JWT (7d)
  store sha256(refresh JWT)
  set cookies, return access JWT

later requests
  verify access JWT
  no session lookup

when the access JWT expires
  verify refresh JWT
  session row must exist
  sha256(presented token) must equal stored hash
  sign a new pair
  replace the stored hash
  if an old refresh JWT appears after that, delete every session

logout
  delete this session id
  clear cookies on this client

logout-alldevices
  delete every session for this user
  clear cookies on this client

second device login
  password check
  insert another session
  previous sessions stay
```

Deleting the user cascades to sessions because the contract says `onDelete: Cascade`.

## 11. What breaks which guarantee

| Event | Access token | Refresh token | Other devices |
|---|---|---|---|
| Access token expires | rejected by `jwt.verify` | still valid | unaffected |
| Refresh succeeds | new one issued | old one stored-hash mismatch | unaffected, they have their own rows |
| Logout | still valid until `exp` | this session row is gone | unaffected |
| Logout all devices | this one valid until `exp` | all rows gone | next refresh fails |
| Reuse detected | existing ones valid until `exp` | all rows gone | next refresh fails |
| Access secret leaks | attacker can mint access tokens | refresh secret is different | you must rotate the secret |
| Refresh secret leaks | still needs the access secret to mint access tokens | attacker can mint refresh JWTs, and they also need a matching hash in the database | minted JWTs fail the hash check unless they can write the database |
| Database leak | password hashes are bcrypt; token hashes are SHA-256 of secrets the attacker does not have | attacker cannot present a hash as a token | users should still reset passwords |
| XSS on the frontend | can call the API while the victim is on the site; cannot read the httpOnly refresh cookie | cannot copy the refresh token out via `document.cookie` | |
| Stolen refresh cookie, before the user refreshes | attacker can refresh and rotate | after they rotate, the user's old cookie looks like reuse and everyone is logged out | that logout is the alarm |

## 12. Layers this module relies on, outside the auth folder

- Zod on register and login rejects a missing email, a bad email, and a password of the wrong length before any hash or query. That is 400, not 401.
- `AppError` plus the error middleware turns expected failures into `{ success: false, message }` and hides unexpected ones behind 500.
- Helmet sets browser security headers. It is not authentication.
- CORS restricts which origin may read the responses from a browser. It is not authentication. Non-browser clients ignore CORS.
- `express.json()` is what makes `req.body.email` exist. Cookie-parser is what makes `req.cookies.refreshToken` exist. Both have to run before the auth routes. They do, in `app.ts`.
- The Temporal polyfill is imported first in `db.ts` because Prisma 8's `createdAt` default needs a global `Temporal` implementation, and Node 22.14 does not have one built in. That is a runtime requirement, not an auth idea.

Rate limiting is not implemented. An interviewer will ask. The honest answer: login, register, and refresh should be limited per IP and per account so password guessing and refresh storms have a ceiling. The dependency may be installed for a later video. The auth routes do not use it yet.

## 13. Interview questions, with answers from this code

Answer from the implementation first, then add the general principle. Interviewers notice when you describe a textbook you did not build.

### Who are you versus what may you do?

Authentication is `authenticate`: verify the access token, set `req.user`. Authorization is `authorize`: compare that user's role to the route's allowed roles. 401 when the token is missing or bad. 403 when the user is known and the role is wrong. In this codebase every token is given the role `USER`, and there is no role column yet. The middleware split is already in place.

### Why not store the password?

A database copy would give it to anyone who reads the table, the backups, or a log. Users reuse passwords. We store a bcrypt hash and compare with `bcrypt.compare`. We never encrypt the password, because encryption is reversible and we never need the original back.

### Why bcrypt and not SHA-256 for the password?

SHA-256 is built to be fast. An attacker who stole the hashes could guess billions of passwords per second on a GPU. bcrypt is slow on purpose, salted per password, and the cost factor (12) can be raised. The salt is inside the hash string, so we do not have a separate salt column.

### Why SHA-256 for the refresh token, then?

The refresh token is already a long random secret. We need a deterministic fingerprint for equality and for a unique column. SHA-256 gives that without bcrypt's 72-byte truncation and without bcrypt's cost. The client must present the original token. The stored hash is not a credential.

### Is a JWT encrypted?

No. It is signed. The payload is readable by anyone holding the string. The signature, HMAC-SHA256 with the server secret, detects modification. `jwt.verify` checks the signature and the expiry.

### Why two tokens?

The access token is sent often and kept short, 15 minutes, so a theft expires quickly. It is not stored, so checking it does not hit the database. The refresh token is sent rarely, lasts 7 days, and is stored as a hash so we can revoke it. One long-lived token cannot be both stateless and revocable.

### Why two secrets?

A refresh token must not verify as an access token. Different secrets make `jwt.verify` fail closed. The `type` claim is a second check.

### What is `sub`?

The standard "subject" claim. We put the user id there. `authenticate` copies it to `req.user.id`.

### Where should the refresh token live in a browser?

In an httpOnly, Secure, SameSite cookie, which is what `setAuthCookies` does. Page JavaScript then cannot read it. The access token is also set as a cookie and copied into the JSON so non-browser clients can send `Authorization: Bearer`.

### What does SameSite=lax actually stop?

The browser will not attach the cookie to a cross-site POST, such as an attacker's form submitting to our API. It will attach it to same-site calls and to top-level GET navigations. Our state-changing auth routes are POST, so the classic CSRF submit is blocked. `SameSite=strict` would also hide the cookie on the top-level navigation that lands on our site from an email link. `lax` is the usual compromise. `none` would send the cookie everywhere and would require `Secure`.

### Why is the refresh route public?

The access token is expected to be expired. Requiring it would make refresh impossible at the moment it is needed. The refresh token is the credential. It is verified inside the service, together with the session row.

### Explain rotation as if I stole a refresh token.

I can call refresh once and get a new pair, and the hash on the row becomes my new token. When the real client refreshes with the token they still have, the hash does not match. The service deletes every session for that user. I lose the session I just created. The user loses their other devices too, which is the signal that something was wrong. They log in with the password again.

If I never use the stolen token, and the user refreshes first, my copy is the one that looks like reuse, and the same wipe happens.

### What if I steal only the access token?

I can call `/me`, `/logout`, and any other protected route until `exp`, at most 15 minutes. I cannot refresh, because I do not have the refresh token. Logout would also kill the victim's session, which is noisy. After 15 minutes the token dies on its own.

### Why does logout not kill the access token immediately?

`authenticate` trusts the signature and `exp` and does not load `sessions`. The design buys a database-free check on every request. The cost is a revocation delay equal to the access lifetime. Say the alternatives: a session lookup per request, or a denylist of token ids in Redis until `exp`.

### How can a user be logged in on two phones?

Each login inserts a session. Logout deletes by session id, not by user id. The tokens carry the session id, so each device refreshes its own row. Logout-all deletes by user id.

### Why store IP and user agent?

Audit and a future "your devices" screen. They are not a second factor. User agent is client-supplied. `req.ip` is the TCP peer and becomes the proxy's address unless `trust proxy` is configured. We do not reject a refresh when the IP changes, because legitimate clients change networks all day.

### How do you stop someone from guessing passwords?

Generic error text so the message does not reveal whether the email exists. bcrypt so each guess is slow. A minimum password length of 8. What I would add next: rate limits on login per IP and per email, and optionally a dummy bcrypt compare when the user does not exist so the timing does not reveal the account. Refresh and register deserve limits too.

### What is a salt, and where is it?

Random data mixed into the password before hashing, so identical passwords produce different hashes. bcrypt stores it in the hash string. We do not have a `salt` column. Refresh-token hashes are unsalted SHA-256 because the input is already unique and high-entropy. A salt there would break the simple equality check unless we stored the salt too. We don't need one.

### What happens if two refreshes race?

Both can pass the hash comparison before either update lands. One client keeps a token that no longer matches. Their next refresh is treated as reuse and all sessions are revoked. The fix is a conditional update: update the row only if `refreshTokenHash` is still the value we verified, and revoke or retry if the update affected zero rows.

### Why can the service be tested without Postgres?

The constructor takes `AuthRepository`, which is an interface. A test can pass an object with the same methods and in-memory arrays. The service rules (duplicate email, generic login error, hash mismatch revokes everyone, expiry deletes one session) can run without Prisma. `auth.container.ts` is the only place that chooses `PrismaAuthRepository`.

### Why are the controller methods arrow functions?

Express calls the handler as a bare function, so a normal method would see `this` as `undefined` and `this.service` would throw. An arrow class field captures the instance as `this`. Service methods stay normal methods because we call them as `this.service.login(...)`, which sets `this`. `private` and `readonly` on the constructor argument are TypeScript: they declare the property, assign it, and stop other files from using it. They are erased at runtime.

### What is inside the access token, field by field?

`sub` user id, `email`, `sessionId`, `type: "access"`, plus `iat` and `exp` added by the library. No password, no hash, no role. Role is filled in by the middleware as `"USER"`.

### How would you add admin routes?

Add a real role source, a column or a membership table. Put the role in the access token or load it in `authenticate`. Pass `authorize("ADMIN")` on those routes. Keep 401 and 403 distinct. Do not trust a role sent by the client in the body. Today, hardcoding `"USER"` means there is nothing to escalate, and also nothing an admin route could check.

### Session cookie versus this design?

A server session stores all state on the server and sends only a random session id. Every request hits the store. Revocation is immediate. A pure JWT stores the claims in the token and does not hit the store. Revocation waits for expiry. This project is in between: stateless access token, stateful rotating refresh token. That is a common production shape for browser apps that want short-lived credentials and the ability to log every device out.

### What would you say is incomplete?

Per-request revocation of access tokens, login rate limits, dummy bcrypt on unknown emails, a locked compare-and-swap on refresh, `trust proxy` for a real client IP behind a load balancer, a session-list API that shows the stored user agent and IP, and password change that revokes all sessions. Knowing those is more convincing than claiming the module is finished.
